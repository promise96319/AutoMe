# 流程图规则

流程图 `flow.html` 用来让用户审阅目标 skill 的执行流程，也是写 SKILL.md 的唯一依据。图上的每一句话，都应当可以直接写进 SKILL.md。

## 1. 流程由什么组成

| 元素 | 定义 |
| --- | --- |
| 步骤 | 一组为同一目的服务的指令，编号为“步骤 1”“步骤 1.1”“步骤 1.1.1”，最多三层。只有步骤有编号，也只有步骤可以作为跳转的目标 |
| 执行指令 | 让 AI 做一件事，写明做什么、做完得到什么 |
| 判断指令 | 根据某个依据做出判断，每种需要不同处理的结果对应一条分支 |
| 提问指令 | 向用户提问并等待回复，必须附带建议；用户的每种回复对应一条分支 |
| 分支 | 写在判断指令或提问指令下面，形式是“如果［结果］，［指令］”，分支里可以继续放任何指令 |
| 流程指令 | 写在分支里或步骤末尾，写明去哪一步、到那里做什么，例如“进入步骤 2”“回到步骤 1.3，重新核对需求”“结束本次任务，交付……” |
| 关键输入和输出 | 步骤之间衔接用的文件或结果，例如前一步生成、后一步读取的文档，或者脚本运行后拿到的结果；写在指令句里，不单独列出 |
| 约束 | 用户明确提出的要求，或者执行、走查中出现偏差后补充的规定，每条一句话 |

## 2. 怎么画

先以需求方案中的实例为线索，从输入一路推到交付结果，画出主线；再挑一两个会走不同路线的情况推一遍，例如输入缺失、中途失败、用户否决，补上分支。修订时，如果原 skill 没有 `flow.html`，先把它的 SKILL.md 如实还原成流程图，标出原文含糊或自相矛盾的地方，再修改受影响的部分，并在图上标出改动。

流程图顶部写名称、触发描述和一句话用途：

- 名称用“动词原形 + 对象”，只用小写字母、数字和连字符，例如 `fix-bug`。
- 触发描述用第三人称，写成“当用户……时使用”，只写什么时候使用，不写怎么做；和已安装的相近 skill 有重叠时，写出能区分的场景。

## 3. 写什么、不写什么

- 只写 AI 不知道、或者必须知道的内容：领域知识、项目约定、容易出错的地方、需要用户参与的地方，以及每种结果的去向。AI 本来就能做好的事，只写目标，不写做法。例如写“找到要修订的 skill”，不写去哪些目录查找；写“确定存放位置”，不展开怎么确定。
- 判断依据写成要识别的意图或条件，不写死用户的具体说法或关键词。例如写“如果是修订”，不写“如果用户说了‘刚才那个’”。
- 用户给出的通常只是一条主线，画图时要主动补全流程上的情况：哪些结果需要不同的处理，哪里要等用户回复，回到前面的步骤后怎样停下来。补全的是流程，不是 AI 本来就会的操作细节；补出来的内容，在交给用户检查时说明。
- 每条指令都写成“做什么，得到什么”；结果的用途不明显时，再写明给哪一步用。做完后不产生任何结果的指令，删掉或并入相邻的指令。
- 正常情况接着往下写，只把需要不同处理的结果写成分支；但每种需要不同处理的结果都必须有分支，判断不了的情况通常写成一条提问分支。
- 执行结果会影响走向时，把这条指令写成判断。
- 提问时，如果是让用户选择，给出选项并标出推荐；如果是向用户要材料，说明需要什么，并给出示例，或者说明拿不到时打算怎么做。
- 尽量少打扰用户：AI 能自己判断和决定的，先自己拿出方案；需要和用户对齐时，交给用户的是一份完整的方案，用户没问题就直接确认，有问题再修改。只有 AI 无法决定、并且会明显影响结果的问题，才附在方案后面请用户选择。
- 回到前面步骤的分支，必须写明怎样停下来，例如“同一个问题修改 2 次仍不通过，结束本次任务，告诉用户卡在哪里”。
- 后面的步骤要用到的东西，在产生它的步骤写明“生成［产物］”，在使用它的步骤写明“根据步骤 N 生成的［产物］”，前后用同一个名字。
- 新建 skill 时，除了用户明确提出的要求，不预先写约束。

## 4. 步骤层级

- 编号只用于步骤，最多三层，优先一到两层。
- 一个步骤要么直接包含指令，要么全部由子步骤组成，不能一部分是指令、一部分是子步骤。
- 需要被跳转到、或者需要在流程图上单独定位的环节，必须是一个步骤；跳转的目标必须是某个步骤的开头。
- 步骤里的指令不编号，按执行顺序排列；每条指令配一个简短名称，写成“动作 → 结果”，例如“读取原 skill → 弄清现状”。

## 5. 生成 flow.html

flow.html 由固定的页面模板生成：把模板复制到目标 skill 的目录下，命名为 `flow.html`，只替换其中 `FLOW_DATA_START` 和 `FLOW_DATA_END` 两行标记之间的内容，写成一个 `const FLOW = {……}` 对象。页面的布局、样式、校验和文字版导出都由模板完成，不要修改模板的其他部分。

FLOW 的字段：

| 字段 | 内容 |
| --- | --- |
| `name`、`description` | 名称和触发描述，规则见第 2 节 |
| `summary` | 一段话说明这个 skill 做什么、交付什么 |
| `globalRules` | 全局约束，每条一句话；没有就写空数组 |
| `resources` | 正文引用的 references、scripts、assets 文件，每项写 `path`、`title`、`purpose` |
| `steps` | 步骤数组，见下文 |

步骤分两种：父步骤写成 `{ id, title, children: [子步骤……] }`；直接包含指令的步骤写成 `{ id, title, body: [指令……], next, rules }`，其中 `next` 是指令执行完后的去向，`rules` 是这一步的约束，都可以省略。

指令和流程指令都是带 `type` 的对象：

| type | 字段 | 含义 |
| --- | --- | --- |
| `do` | `label`、`text` | 执行指令 |
| `decide` | `label`、`text`、`branches` | 判断指令 |
| `ask` | `label`、`text`、`branches` | 提问指令；写在分支里、问完按回复继续的提问，可以不写 `branches` |
| `check` | `label`、`text`、`items` | 带清单的指令，`items` 是清单项 |
| `goto` | `to`、`text` | 进入或回到步骤 `to`；`text` 写到那里做什么，可以省略。页面按步骤的先后，自动写成“进入”或“回到” |
| `retry` | `text` | 在本步骤内重做，导出为“然后……” |
| `end` | `text` | 结束，写明交付什么或要告诉用户什么，并包含“结束本次任务” |

分支写成 `{ when, label, then: [……] }`：`when` 是完整的条件；`label` 是简短名称，可以省略；`then` 是命中后依次执行的指令，可以包含流程指令。

填写要求：

- `text` 写完整的句子，但不带句末标点，标点由导出时补上。
- `label` 写成“动作 → 结果”的简短名称。
- 引用文件时，用反引号写出路径，例如 `` `references/foo.md` ``，并在 `resources` 中登记。

示例：

```js
{ id: '1.2', title: '读懂要修订的 skill', body: [
  { type: 'decide', label: '读取原 skill → 弄清现状与期望', text: '读取要修订的 skill，写清它现在的表现和期望的表现', branches: [
    { when: '找不到这个 skill', label: '找不到', then: [
      { type: 'ask', label: '问是否改为新建', text: '询问用户是否改为新建，并给出建议', branches: [
        { when: '用户同意', then: [{ type: 'goto', to: '1.3' }] },
        { when: '用户不同意', then: [{ type: 'end', text: '结束本次任务' }] },
      ] },
    ] },
  ] },
], next: { type: 'goto', to: '1.4' } }
```

生成后，在浏览器中打开 flow.html：顶部显示“结构校验通过”才算完成；有问题时，页面会列出每个问题。页面的“文字版”可以直接导出 SKILL.md 的初稿。

## 6. 自查清单

- [ ] 没有描述 AI 本来就能做好的事，也没有写死用户的具体说法。
- [ ] 每条指令都写明了做完得到什么。
- [ ] 每种需要不同处理的结果都有分支，每个提问都附带了建议。
- [ ] 每个结果都有去向，每个步骤从步骤 1 出发都走得到。
- [ ] 每个回到前面的分支都写明了怎样停下来。
- [ ] 每个“根据步骤 N 生成的［产物］”都能在步骤 N 找到对应的“生成［产物］”，并且前后名字一致。
- [ ] 步骤层级不超过三层，没有一个步骤同时包含指令和子步骤。
- [ ] 用实例沿流程图走一遍，能到达期望的结果。
