# 把流程图写成 SKILL.md

SKILL.md 的内容来自用户确认的 `flow.html`。先用 flow.html 页面中的“文字版”导出初稿，再做串联和措辞整理；不增加图上没有的步骤、分支或去向。修改了正文时，同步修改 flow.html 中的流程数据，保持两者一致。

## 1. 文件结构

SKILL.md 依次包含三部分：

1. frontmatter，包含 `name` 和 `description`，取自流程图顶部。
2. 开头用一段话说明这个 skill 做什么、交付什么；有全局约束时，紧接着写在“约束：”下面。
3. “工作流”模块，按流程图逐步写出全部步骤，步骤编号与流程图一致。

## 2. 写什么、不写什么

- 只写 AI 不知道、或者必须知道的内容：领域知识、项目约定、容易出错的地方、需要用户参与的地方，以及每种结果的去向。AI 本来就能做好的事，只写目标，不写做法，一句话能说清的不展开。
- 判断依据写成要识别的意图或条件，不写死用户的具体说法或关键词。
- 正常情况接着往下写，只把需要不同处理的结果写成分支。
- 提问指令必须附带建议：让用户选择时，给出选项并标出推荐；向用户要材料时，说明需要什么，并给出示例或拿不到时的做法。
- 尽量少打扰用户：AI 能自己判断和决定的，先自己拿出方案；需要和用户对齐时，交给用户的是一份完整的方案，用户没问题就直接确认，有问题再修改。只有 AI 无法决定、并且会明显影响结果的问题，才附在方案后面请用户选择。
- 不要把并列的条件写成先后的步骤，也不要用重复说明和琐碎的步骤盖过主线。

## 3. 步骤和指令的写法

| 元素 | 写法 |
| --- | --- |
| 步骤 | 一级步骤写成 `### 步骤 1：名称`，子步骤写成 `#### 步骤 1.1：名称`，第三层写成 `##### 步骤 1.1.1：名称`。层级规则与流程图相同：最多三层，优先一到两层；一个步骤要么直接写指令，要么全部由子步骤组成 |
| 指令 | 不编号，用连贯的指令式句子按顺序写，每句写明做什么、做完得到什么；几件事之间用“然后”“找到后”“最后”等词衔接 |
| 分支 | 写在判断指令或提问指令下面，用 `- 如果……，……`，一律以“如果”开头；分支和循环在所属步骤内展开 |
| 清单 | 写在指令下面，用 `- [ ] ……`，表示每一项都要核对 |
| 流程指令 | 写明去哪一步、到那里做什么，例如“进入步骤 2”“回到步骤 1.3，重新核对需求”“结束本次任务，交付……”；回到前面步骤的分支，写明怎样停下来 |
| 关键输入和输出 | 不单独列出，写进指令句里：使用的地方写“根据步骤 N 生成的［产物］，……”，产生的地方写“……，生成［产物］”；只写步骤之间衔接用的内容，前后用同一个名字 |
| 去向 | 步骤的指令执行完、又没有遇到流程指令时，在步骤末尾写“完成后进入步骤 N” |
| 约束 | 写在出现偏差的步骤末尾的“约束：”下面，用无序列表，每条是一句完整的话，需要说明原因时写在同一句里 |

## 4. 约束的来源

- 约束只来自三处：用户明确提出的要求；执行或走查中出现的偏差；修订时用户纠正的偏差。新建时不预先写其他约束。
- 对所有步骤都适用的约束，写在开头说明之后的全局约束里；其余的写在它生效的步骤里，不集中堆在开头或末尾。

## 5. 引用

- 引用 skill 包内的文件时使用相对路径，例如 `references/foo.md`；不要使用 `@` 语法。
- 在用到它的那一步引用，例如“按 `references/foo.md` 判断……”，不把引用文件的内容摘要复述到 SKILL.md 中。
