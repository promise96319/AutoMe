# 写 skill 的规则

skill 的内容分为流程和规则两类：流程用指令写，规定 AI 按什么顺序做什么；规则用约束写，规定 AI 做事时必须或不得怎样。写 skill 时，必须遵守以下要求，写完后逐条对照检查。

## 1. 名称和描述

- **名称用“动词 + 名词”的结构**，小写，用连字符连接，例如 `create-skill`、`fix-bug`。
- **描述用第三人称写成“当……时使用。例如“xxx”、“yyy”等”**，例子举两三个具体的请求。

## 2. 流程

### 2.1 骨架

流程写在 SKILL.md 的“工作流”中，由步骤组成，步骤由指令组成，整体是这个形状：

```markdown
### 步骤 1：［这一步做什么］

#### 步骤 1.1：［这一步做什么］

［执行指令：做什么，得到什么。］

［判断指令：根据什么，判断什么：］

- 如果［结果 A］，进入步骤 1.2。
- 如果［结果 B］，［指令］，然后重新［……］。

［提问指令：问用户什么，并给出建议。等待回复：］

- 如果用户［回复 A］，［指令］。
- 如果用户［回复 B］，结束本次任务，交付［……］。

完成后进入步骤 1.2。

约束：

- ［一句完整的约束。］
```

### 2.2 各部分

- **步骤**是为一个目的服务的一组指令，名称写成这一步做什么，编号为“步骤 1”“步骤 1.1”“步骤 1.1.1”，最多三层。一个步骤要么只有指令，要么只有子步骤；需要跳转到的地方，必须是一个步骤。
  - **指令**按执行顺序排列，不编号，分三种：
    - **执行**：写明做什么、得到什么。结果会影响走向时，改写成判断。
    - **判断**：写明根据什么判断；每种需要不同处理的结果写一条分支，正常情况直接往下写。
    - **提问**：写明问什么，并附上建议；用户的每种回复写一条分支。只在无法自行决定、且影响结果时提问。
  - **分支**写在判断或提问下面，形式为“如果［结果］，［指令］”，里面可以继续放任何指令。
  - **流程指令**决定去向，只有四种：进入步骤 N；回到步骤 N，重新……；然后重新……；结束本次任务，交付……。
  - **去向**：每个步骤结束时都要有去向；没有流程指令时，在步骤末尾写“完成后进入步骤 N”。

### 2.3 贯穿全程

- **补全流程，不补操作。** 从主线出发，补全每种结果的去向，不补 AI 本来就会的操作。
- **产物写进指令句，前后同名。** 生成处写“生成［产物］”，使用处写“根据步骤 N 生成的［产物］”。
- **回退必须能停。** 回到前面步骤的分支，写明终止条件。

## 3. 规则

### 3.1 放在哪里

- 只在某一步生效的规则，写在该步骤末尾的“约束：”下面。
- 对所有步骤都适用的规则，写在工作流之前的“约束：”下面。
- 篇幅大、自成体系的规则，按第 4 节拆进 `references/`。

### 3.2 从哪里来

- **规则只来自用户明确提出的要求，以及执行或走查中出现的偏差。** 不得预先写规则。

### 3.3 怎么写

- **每条规则写明条件、对象、强度和行为**，即“在什么情况下，对什么，必须 / 不得 / 可以怎样做”。条件不言自明时，可以省略。
- **按规则的性质选择写法：**

  | 规则的性质 | 写法 |
  | --- | --- |
  | 规定形式：结果长什么样 | 给出模板 |
  | 规定构造：由哪些部分组成 | 先给出整体结构，再逐一定义各部分 |
  | 规定取舍：在几种做法中选择 | 先说明在平衡什么，再按条件给出做法，并给出区分的判据 |
  | 规定行为：必须或不得做什么 | 用一句话写明条件、强度和行为 |
- **提炼规则本身，不罗列、不重复。** 能由其他规则推出的，不单独写；规则抽象到难以判断如何执行时，可以附一个简短的关键实例。

## 4. 拆分

拆分是在“一眼看完”和“按需加载”之间取平衡：SKILL.md 每次触发都会整篇加载，拆出去的文件只在用到时才读取。

### 4.1 什么时候拆

- **内容少时不拆。** 规则只有几句话时，直接写在 SKILL.md 里。
- **超过 200～300 行且还在增长时，拆出能独立存在的部分。** 规则、说明、知识、模板等离开主流程也能单独读懂的内容，按 4.2 节拆出去，SKILL.md 只留主流程。
- **输入、处理、输出都固定、能用程序完成的环节，写成脚本。** 放进 `scripts/`，由工作流调用并根据结果继续。

### 4.2 拆到哪里

| 目录 | 放什么 | 执行时怎么用 |
| --- | --- | --- |
| `references/` | 需要 AI 读懂才能照着做的内容：规则、说明、领域知识、决策依据 | 执行到对应步骤时读取，理解后遵守 |
| `assets/` | 不需要 AI 读懂的半成品：模板、占位文件、原始数据 | 拿来填空或原样输出 |
| `scripts/` | 确定性的处理逻辑 | 直接运行，根据结果继续 |

区分 references 和 assets 只看一点：AI 要读懂它才能做事的，放 references；AI 只是拿来用、不需要懂的，放 assets。

### 4.3 拆出后怎么命名和使用

- **一份文件只负责一件事，文件名说明它管什么。** 文件名用小写英文和连字符。
- **开头告诉 AI 这份文件讲什么、什么时候用。**
- **在用到的那一步引用。** 写明按哪个文件做哪件事，用相对路径，不用 `@`，不把文件内容复述进 SKILL.md。
- **引用只有一层。** 所有文件都由 SKILL.md 直接引用，被引用的文件不再引用别的文件。

## 5. 通用规则

- **仅写入 AI 不具备的信息**：每一句都须经受“AI 是否确实需要”的检验，AI 已知或已能胜任的内容不写。
- **以可衡量的条件替代模糊表述**：不使用“尽量”“适当”等无衡量标准的词，要求的强度仅用“必须”“不得”“可以”。
- **同一概念始终使用同一术语**：例如前文称“需求方案”，后文不得改称“需求文档”或“方案”。
