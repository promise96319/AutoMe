# create-skill

## 工作流

### 步骤 1：明确要开发什么样的 skill

#### 步骤 1.1：识别用户意图

识别用户是要修订已有的 skill 还是新建；新建时，按 `references/decisions.md` 判断这个需求是否适合做成 skill：

- 如果是修订，进入步骤 1.2。
- 如果是新建，并且适合做成 skill，进入步骤 1.3。
- 如果是新建，但不适合做成 skill，推荐 `references/decisions.md` 中对应的做法，询问用户是否改用：
  - 如果用户接受，按推荐的做法处理，结束本次任务。
  - 如果用户仍要做成 skill，进入步骤 1.3。
- 如果无法确定，询问用户，并给出你的判断和理由，然后按回复重新识别。

#### 步骤 1.2：读懂要修订的 skill

读取要修订的 skill 和同目录下的 `skill-workflow.html`，写清它现在的表现和期望的表现，并找一个能复现现状的请求，供步骤 3.2 验证：

- 如果找不到这个 skill，询问用户是否改为新建，并给出建议：
  - 如果用户同意，进入步骤 1.3。
  - 如果用户不同意，结束本次任务。
- 如果它位于插件缓存等由别人维护的位置，提醒用户原处修改会在插件更新时被覆盖，建议复制到个人 skill 目录后再改。

完成后进入步骤 1.4。

#### 步骤 1.3：确认新 skill 的定位

检查已安装的 skill 中有没有用途相近的，并确定新 skill 的存放位置：

- 如果有用途相近的 skill，询问用户是修订它还是新建，并给出推荐：
  - 如果用户选修订，回到步骤 1.2。
  - 如果用户选新建，继续确定存放位置。
- 如果无法确定存放位置，询问用户，并给出推荐。

完成后进入步骤 1.4。

#### 步骤 1.4：形成并确认需求方案

根据前面了解到的情况，自己形成需求方案，作为步骤 2.1 画流程图的依据；方案对以下每一项都给出你的判断：

- [ ] 要解决什么问题，没有这个 skill 时 AI 通常会怎么做错。
- [ ] 什么情况下使用，哪些相近的请求不该触发它。
- [ ] 输入什么，交付什么，做到什么程度算完成。
- [ ] 打算怎么做，大致分哪几步。
- [ ] 哪些地方需要用户参与。
- [ ] 用户明确提出了哪些要求，这些要求在步骤 3.1 写成约束。
- [ ] 用来验证的具体实例，包括真实的输入和期望的结果；修订时使用步骤 1.2 找到的复现请求。

把需求方案交给用户确认。只有你无法自行决定、并且会明显影响结果的问题，才附在方案后面，给出选项并标出推荐。等待回复：

- 如果用户确认，进入步骤 2.1。
- 如果用户提出修改或补充，按意见更新需求方案，然后再请用户确认。

约束：

- 用户确认后的需求方案是后续步骤的依据，后面的步骤如果发现需要偏离它，回到步骤 1.4 修改方案，并重新请用户确认。

### 步骤 2：生成并确认流程图

#### 步骤 2.1：画出流程图

根据用户在步骤 1.4 确认的需求方案，按 `references/skill-rules.md` 写出目标 skill 的流程和规则，再以 `assets/flow-template.html` 为模板、按 `references/flowchart.md` 生成 skill 目录下的 `skill-workflow.html`；修订时，在原有的 `skill-workflow.html` 上只改受影响的部分。

画图时遇到拿不准的地方：

- 如果是方向性的问题，也就是有几种合理做法、选哪种结果明显不同，并且无法根据需求方案自行决定，询问用户，给出 2～3 个建议并标出推荐。
- 如果只是局部细节，自行决定，并在步骤 2.2 交给用户时说明。

画完后，按 `references/skill-rules.md` 逐条检查并改好。

完成后进入步骤 2.2。

#### 步骤 2.2：请用户确认流程图

把 `skill-workflow.html` 交给用户检查，说明主线、关键判断和你自行决定的细节；修订时说明改了哪里。等待回复：

- 如果用户确认，进入步骤 3.1。
- 如果用户指出需求理解有误，回到步骤 1.4，重新修改需求方案。
- 如果用户指出流程图本身的问题，修改 `skill-workflow.html` 并重新自查，然后再请用户确认。
- 如果用户要暂停，保存当前的 `skill-workflow.html`，告诉用户下次从步骤 2.2 继续，结束本次任务。

### 步骤 3：写成 SKILL.md 并走查

#### 步骤 3.1：按流程图写正文

根据用户在步骤 2.2 确认的 `skill-workflow.html`，按 `references/writing.md` 写出 SKILL.md，按 `references/skill-rules.md` 写出需要拆分的文件；修订时只改受影响的部分。

运行 `scripts/embed-resources.py`，把引用文件的内容写入 `skill-workflow.html`。

完成后进入步骤 3.2。

#### 步骤 3.2：走查正文

按 `references/walkthrough.md` 走查步骤 3.1 写出的 SKILL.md，得到走查结果，再根据结果处理：

- 如果同一个问题已经修改 2 次仍不通过，结束本次任务，交付当前的 SKILL.md，并告诉用户卡在哪里、你建议怎么改。
- 如果正文与流程图不一致，或者执行时因为正文含糊而走错，按 `references/skill-rules.md` 修改正文，然后重新走查。
- 如果正文清楚，但执行时仍然出现偏差，在出现偏差的步骤补一条约束，然后重新走查。
- 如果流程图本身有问题，回到步骤 2.1，修改流程图，并重新请用户确认。
- 如果触发判断有误，修改触发描述并同步到 `skill-workflow.html` 顶部，然后重新走查。
- 如果都通过，结束本次任务，交付最终的 SKILL.md、`skill-workflow.html` 和走查结果，并说明你自行决定的内容和仍待用户决定的事项。
