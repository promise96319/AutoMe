# 1 Skill 流程元素模型

本文定义 skill 流程由哪些元素组成、每类元素怎么写、怎么展示，以及写作时必须遵守的几条规则。请你确认。确认后，create-skill 的数据、文字版导出、流程页展示和生图规则都以它为准。

**核心结论**：skill 由**步骤**组成。每个步骤是一串按顺序执行的**指令**，指令只有三种：执行、判断、提问。判断和提问会产生**分支**；分支里放的也是指令，其中包括“进入步骤 N”“回到步骤 N，重新……”“结束本次任务”这类**流程指令**。每个步骤只写出**衔接用的关键输入和输出**。**约束**一开始没有，在执行或走查中出现偏差后，才逐条补充。

> 1.1～1.6 节是你提出的模型。1.7 节是我检查后补充的写法规则，以及对模型的三处调整，请重点看。

## 1.1 元素组成

图 1 展示元素之间的关系。

```
Skill：名称、触发描述、一句话用途、全局约束（可以没有）
└── 步骤 N：名称（只放子步骤，或者只放指令，二者选一）
    └── 步骤 N.M：名称（最多再分一层 N.M.K，优先只用两层）
        ├── 执行指令（不编号，按顺序用连贯的句子写；关键输入输出写在句子里，例如“根据用户在步骤 1.4 确认的需求方案，……，生成 skill-workflow.html”）
        ├── 判断指令 ──┬── 如果［结果 A］，指令……（可以包含流程指令）
        │              └── 如果［结果 B］，指令……
        ├── 提问指令 ──┬── 如果用户［回复 A］，指令……
        │              └── 如果用户［回复 B］，指令……
        ├── 去向（指令中没有流程指令时，写明完成后进入哪一步）
        └── 约束（无序列表，每条一句话，出现偏差后逐条补充）
```

## 1.2 指令

指令是给 AI 的一句话命令，在步骤内按顺序执行，不编号。**每条指令都要有始有终：写明做什么，也写明做完得到什么。** 只写动作、不交代结果的指令，AI 不知道做到什么程度算完成，也看不出这一条为什么存在。

指令分为三种，每种的“有始有终”体现在不同的地方：

| 种类 | 作用 | 要求 | 例子 |
| --- | --- | --- | --- |
| 执行指令 | 让 AI 做一件事 | 写成“做什么，得到什么”；结果的用途不明显时，再写明给哪一步用 | 完整读取原 SKILL.md 和它引用的文件，弄清它现在什么时候触发、每一步怎么做，作为确定修改范围的依据 |
| 判断指令 | 让 AI 做出判断，得到明确的结果 | 写成“依据什么，判断什么”，并列出所有可能的结果，每个结果对应一条分支 | 根据用户的请求，判断要新建还是修订 skill |
| 提问指令 | 向用户提问，等待回复 | 写成“问什么，为了确定什么”，并附带建议：让用户选择时，给出选项并标出推荐；向用户要材料时，说明需要什么，并给出示例或拿不到时的默认做法。用户的每种回复对应一条分支 | 询问用户是否改为新建，以决定是否继续本次任务，并说明你的建议 |

**判断一条指令写得是否合格**，问三个问题：

1. 做完这一条，手里多了什么？说不出来，就补上结果。
2. 这个结果后面有人用吗？没人用，就删掉这一条，或者并入相邻的指令。
3. 能看出这一条是否做完了吗？看不出来，就把结果写具体。

用途只在不明显时才写，不要每条都加“为了……”。例如“理解用户意图”的用途就很明显，不需要写。

三种指令写法相同，都是步骤里按顺序书写的连贯句子；几件事之间用“然后”“找到后”“最后”等词衔接。判断指令和提问指令下面接着写分支。

### 1.2.1 步骤层级

- 编号只用于步骤，最多三层（1、1.1、1.1.1），优先使用一到两层。
- 一个步骤要么直接写指令，要么全部由子步骤组成，不能一部分是指令、一部分是子步骤。
- 凡是需要被跳转到、或者需要在流程图上单独定位的环节，都必须是一个步骤；步骤里的指令较多，或者其中某个环节需要被单独跳回时，拆成子步骤。

## 1.3 分支与流程指令

分支写在判断指令或提问指令下面，形式是“如果［结果］，［指令］”。分支里可以放任何指令，包括再判断、再提问，以及流程指令。流程指令的用词按语境自然地写，硬性要求只有一条：**写明去哪一步，以及到那里做什么**。常见的写法如下：

| 流程指令 | 写法 | 说明 |
| --- | --- | --- |
| 进入步骤 | `进入步骤 N` | 往后走，或者转到另一条路径 |
| 回到步骤 | `回到步骤 N，重新……` | 回到前面的步骤，“重新”后面写明要重做什么，例如“回到步骤 1.3，重新核对需求” |
| 本步重做 | `然后重新……` | 在本步骤内再做一遍，例如“请用户指认后，重新查找” |
| 结束 | `结束本次任务，……` | 写明结束时交付什么，或者要告诉用户什么 |

步骤的指令全部执行完、又没有遇到流程指令时，在步骤末尾写明去向，例如“完成后进入步骤 3”。

## 1.4 关键输入与输出

每个步骤都有输入输出，但 AI 能自己理解的不必写出来。必须写出来的，是步骤之间衔接用的：前一步产生、后一步要用的文件或结果，以及脚本运行后拿到的结果。

写法：不单独列出“输入”“输出”，而是写进指令句里。使用的地方写“根据步骤 N 生成的［产物］，……”，产生的地方写“……，生成［产物］”。例如步骤 2.1 写“根据用户在步骤 1.4 确认的需求方案，……，保存为 skill-workflow.html”，步骤 3.1 写“根据用户在步骤 2.2 确认的 skill-workflow.html，写出 SKILL.md”。

## 1.5 约束

写好的指令如果能让 AI 正确执行，就不需要约束。约束来自偏差：AI 在某一步做偏了，被纠正后，才在这一步补一条，防止再犯。

| 规则 | 说明 |
| --- | --- |
| 形式 | 无序列表，每条是一句完整的话；需要说明原因时，写在同一句里 |
| 位置 | 写在出现偏差的步骤末尾；对所有步骤都适用的，写在 skill 开头的全局约束里 |
| 来源 | 执行中出现的偏差、写完后走查发现的偏差，或者用户明确提出的要求 |
| 初始状态 | 新建 skill 时，除了用户明确提出的要求，不预先写约束 |

## 1.6 写法示例

以 create-skill 的步骤 1.2 为例：

```markdown
#### 步骤 1.2：读懂要修订的 skill

读取要修订的 skill 和同目录下的 `skill-workflow.html`，写清它现在的表现和期望的表现，并找一个能复现现状的请求，供步骤 3.2 验证：

- 如果找不到这个 skill，询问用户是否改为新建，并给出建议：
  - 如果用户同意，进入步骤 1.3。
  - 如果用户不同意，结束本次任务。
- 如果它位于插件缓存等由别人维护的位置，提醒用户原处修改会在插件更新时被覆盖，建议复制到个人 skill 目录后再改。

完成后进入步骤 1.4。
```

这个例子只写了 AI 不知道的内容：要一并读取 `skill-workflow.html`、要找复现请求、插件缓存里的文件会被覆盖。至于怎么查找、怎么读文件，AI 本来就会，所以不写。

## 1.7 补充：写法规则与模型调整

按你的模型逐类检查后，下面这些情况如果不写清楚，AI 会卡住、陷入循环，或者自己猜着往下走。

### 1.7.1 写法规则

这几条规则约束的是“怎么写 skill”，写进生图规则和 create-skill 的写作要求，不需要写进每个 skill 里。

| 规则 | 原因 | 例子 |
| --- | --- | --- |
| 判断的结果必须覆盖所有情况；判断不了的情况，通常写成一条提问分支 | 结果没覆盖到时，AI 只能自己猜 | 判断新建还是修订时，加上“如果无法判断，询问用户……” |
| 执行结果会影响走向时，把它写成判断 | 执行指令本身没有分支，结果不同时 AI 不知道往哪走 | “读取原文：如果找不到……；如果找到了……” |
| 回到前面步骤的分支，必须写明怎样停下来 | 否则可能无限循环 | “回到步骤 2，重新修改流程图；同一问题修改 2 次仍不通过，结束本次任务，告诉用户卡在哪里” |
| 跳转的目标必须是某个步骤的开头；需要回到某一步中间时，把那一步拆开 | 只有步骤有编号可以跳转 | 需要反复执行“请用户检查”时，把它单独拆成一步 |
| 后面步骤要用到的东西，在产生它的步骤写明“生成［产物］”，在使用它的步骤写明“根据步骤 N 生成的［产物］”，前后用同一个名字 | 保证衔接清楚，也便于自动检查 | 步骤 2.1 “……，保存为 skill-workflow.html”；步骤 3.1 “根据用户在步骤 2.2 确认的 skill-workflow.html，……” |
| 只写 AI 不知道或必须知道的内容；AI 本来就能做好的事只写目标，不写做法，一句话能说清的不展开 | 写 AI 已经会的事是废话，还会冲淡真正重要的内容 | 写“找到要修订的 skill”，不写去哪些目录查找；写“确定存放位置”，不展开怎么确定 |
| 判断依据写成要识别的意图或条件，不写死用户的具体说法 | 写死说法会漏掉其他表达，AI 也会机械匹配 | 写“如果是修订”，不写“如果用户说了‘刚才那个’” |
| 正常情况接着往下写，只把需要不同处理的结果写成分支 | 把每个正常结果都列成分支会显得啰嗦 | “读取原 skill……：如果找不到……”，找到了就接着往下写 |
| 每条指令写成“做什么，得到什么”，做完后不产生任何结果的指令删掉或合并 | 只有动作的指令，AI 不知道做到哪里算完成，审阅者也看不出它为什么存在 | “读取原文”改为“完整读取原文，弄清它现在每一步怎么做，作为确定修改范围的依据” |
| 指令下面的清单项用 `- [ ]`，分支一律以“如果”开头 | 两者都是列表，靠写法区分“逐项核对”和“只走一条” | `- [ ] 解决什么问题：……` |

### 1.7.2 对模型的三处调整

1. **在 skill 层增加全局约束。** 有些偏差和具体步骤无关，例如回复语言、用户的回答不在给出的选项里时怎么办。全局约束和步骤约束遵守同样的规则：一开始没有，出现偏差后再加。
2. **约束的来源加上“走查发现的偏差”。** create-skill 写完 skill 后会用实例走查，走查发现的偏差和正式使用中的偏差一样，也补成约束。这样约束可以在发布之前就积累起来。
3. **明确“提问附带建议”的含义。** 让用户选择时，给出选项和推荐；向用户要材料时，说明需要什么，并给出示例或拿不到时的默认做法。

另外两种情况不单独设元素，按下面的方式写：

| 情况 | 写法 |
| --- | --- |
| 运行脚本、使用子 skill | 写成执行指令；结果会影响走向时写成判断；拿到的结果写成输出 |
| 对一组对象逐个处理 | 写成一条执行指令：“对每个……依次执行：”，下面嵌套有序的子指令 |

## 1.8 展示方式

| 元素 | 展示 |
| --- | --- |
| 步骤 | 卡片，标题为“步骤 N · 名称”，子步骤缩进在父步骤下面 |
| 执行 / 判断 / 提问指令 | 类型标签加完整原句，不另写简短名称，也不提供简洁模式；流程图上展示的就是 SKILL.md 的原文 |
| 分支 | 一行写成“如果［结果］→ 指令 → 流程指令” |
| 进入步骤 / 回到步骤 | “→ 步骤 N”或“↺ 回到步骤 N”的标记，点击跳转；“回到”同时显示要重做的内容 |
| 结束 | 终点标记，写明交付什么或告诉用户什么 |
| 关键输入和输出 | 在指令句中标出关键产物，并在产生它和使用它的步骤之间互相链接 |
| 约束 | 卡片底部的无序列表；没有约束的步骤不显示这一块；全局约束显示在页面顶部 |

## 1.9 对现有 create-skill 的影响

| 方面 | 调整 |
| --- | --- |
| 去向 | 按 1.3 节改写，每个去向都写明去哪一步、到那里做什么 |
| 输入输出 | 不再单独列出，写进指令句里，只保留衔接用的，并且前后同名 |
| 指令 | 逐条改写成“做什么，得到什么”，删掉或合并不产生结果的指令 |
| 提问 | 每个提问指令都补上建议 |
| 约束 | 只保留用户明确提出的要求；我自行添加的删掉，其中属于判断依据的，放进对应的判断指令 |
| 写法规则 | 按 1.7.1 节逐条检查并补全，例如判断新建还是修订时，补上“无法判断”的分支；检查不通过的回路，补上停止条件 |
| create-skill 自身的行为 | 写 skill 时遵守本模型；新建时不预先写约束；修订时，如果用户是在纠正偏差，就在对应步骤补一条约束；走查发现的偏差也补成约束 |
