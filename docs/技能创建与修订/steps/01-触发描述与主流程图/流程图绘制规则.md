# 1 怎样把 skill 画成可审查的流程

审阅者应能拿着一个具体请求，从入口推演到结果，并指出某个错误该回到哪一步修改。画图前先梳理执行逻辑，再按复杂度决定用一张图、几张局部图，还是图和表的组合。

## 1.1 交代每一步怎样改变输入

从一个应当触发 skill 的请求开始，说明它带来哪些材料，怎样的结果才算完成。沿主线给步骤命名，并用动词写明实际动作。审阅每一步时，以下四项应该能放在一起读。

| 要看什么 | 写到什么程度 |
| --- | --- |
| 输入 | 写出这一步实际使用的材料、状态或上一步的产物。 |
| 动作 | 写明对输入做什么处理或判断。例如“用复现时的输入重跑”，比“做好验证”更容易执行。 |
| 结果 | 写出能检查的产物或状态，以及谁在下一步使用它。例如重跑后的实际输出，可以用来判断原问题是否消失。 |
| 规则 | 把确实影响当前动作的约束放在该步旁边。只收入明确要求或实际遇到的问题。 |

## 1.2 让每种结果都有去向

在出现选择的地方写清**条件 → 结果 → 去向**。能继续就指向具体步骤。需要等待时，写明缺什么、收到后从哪一步恢复。结束时写明已经交付什么或为何结束。循环应标出回到哪一步、什么变化值得再试、满足什么条件可以退出。

例如，走查一个新 skill 时，如果请求选对了，流程也走通了，但执行者仍不知道要比较哪两个值，结果就是定位到一条不完整的正文指令。返回编写正文的步骤，补清比较对象，再用同一输入复核。若结果符合预期即可交付。

## 1.3 按审阅问题选择形式

- **看路径。** 先让入口、主步骤和完成结果可以顺序阅读。分叉或回跳影响实际执行时才画。用步骤名或编号识别去向，颜色、形状和位置可辅助阅读。
- **看细节。** 简单流程可以直接在节点旁列输入、结果和约束。节点文字变长时，把这些内容放进同编号的步骤表。一个判断有多种结果时，局部决策表可以逐行对照条件和去向。
- **方便改。** 一条规则在它生效的地方维护。图、表和正文使用相同的步骤名或编号。修改某一步的产物时，沿下游查谁在使用它。修改分支时，同时核对返回点和结束条件。

## 1.4 用场景验收

用一个正常请求走到交付，再选一个确实会改变去向的场景走一遍。审阅者应能指出：**在哪一步、拿到什么输入、依据哪条规则、得出什么结果、下一步去哪。** 若还得靠猜，回到缺信息的步骤或分支补清。涉及回路时，再验证补充材料或修正后能否退出。
